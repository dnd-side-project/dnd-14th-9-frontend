# ADR — SSR 백엔드 직행과 브라우저 BFF 유지 (#378)

- 상태: 구현·로컬 검증 완료. #380 병합 후 PR 기준 diff를 최종 확인한다.
- 범위: Server Component 및 서버 prefetch의 조회 요청. 브라우저 인증 요청과 변경 요청은 제외한다.

## 맥락

현재 서버 조회 중 일부는 프런트 `/api` Route Handler를 다시 호출한 뒤 백엔드로 전달된다. 서버는 `HttpOnly` 쿠키를 읽어 백엔드의 `Authorization: Bearer` 헤더를 직접 만들 수 있다. 브라우저 JavaScript는 그 쿠키를 읽지 못하므로 보호 API 호출에 프런트 BFF가 필요하다. 백엔드 CORS는 `Authorization` 헤더를 허용하지만 토큰 접근 제약을 해결하지는 않는다.

## 결정

SSR 조회에 필요한 얇은 `server-only` endpoint 함수를 두고 백엔드를 직접 호출한다. 브라우저 endpoint 함수와 `/api` Route Handler는 유지한다. 공통 응답 타입, fetch/오류 처리, React Query 키는 공유하고 서버 prefetch의 `queryFn`만 직행 함수로 지정한다. #362에서 적용된 세션 상세 경로를 기준으로 한다.

## 검토한 선택과 비용

| 선택 | 이점 | 비용과 판단 |
| --- | --- | --- |
| self-hop 유지 | endpoint 함수 하나를 계속 사용 | SSR 왕복과 Proxy 재진입이 남아 #378 목적을 달성하지 못한다. |
| **SSR 직행 + 브라우저 BFF 유지** | SSR 왕복 제거, 브라우저 JavaScript에 토큰 비노출, 기존 인증 흐름 유지 | 얇은 endpoint 함수가 둘이 되어 경로·옵션 차이가 생길 수 있다. 양쪽 경로 테스트와 공유 타입·전송 함수로 관리한다. |
| 액세스 토큰을 브라우저 메모리에 두고 직접 호출 | 브라우저의 BFF 경유도 제거 가능 | XSS 시 토큰 노출, 새로고침·갱신·SSR 인증 재설계가 필요하다. SSR self-hop 제거에 필요한 범위를 넘는다. |
| 백엔드 쿠키 인증으로 변경 | 브라우저가 `Bearer` 헤더를 만들지 않아도 된다 | 백엔드 인증 계약·쿠키 범위 변경과 CSRF 검토가 필요하다. 프런트 단독 작업이 아니다. |
| 단일 endpoint 함수의 런타임 분기 | endpoint 함수 중복 감소 | 호출 경로와 `server-only` 경계가 덜 분명해진다. 이미 공통 전송 함수가 있으므로 분리 비용이 작다. |

## 검증과 남은 위험

대상 SSR 조회의 self-call 수, 백엔드 호출 수, Document TTFB와 문서 응답 완료 시간을 변경 전후 같은 조건에서 기록한다. Next 스트리밍으로 첫 바이트가 서버 조회 완료보다 먼저 나올 수 있으므로 TTFB만으로 효과를 판정하지 않는다. 보호 페이지에서 Proxy 갱신 직후 서버 조회가 새 쿠키를 읽는지 검증한다. 실측 결과가 개선되지 않으면 그대로 PR에 기록한다. 브라우저 호출 경로는 유지되므로 브라우저 `/api` 호출 수 감소를 이 결정의 효과로 주장하지 않는다.

로컬 공개 경로 `/session/694/edit`의 20회 측정에서는 SSR self-call이 코드/테스트상 1→0이고 백엔드 호출은 1→1이다. Document TTFB 중앙값은 6.67→5.10ms, 응답 완료 중앙값은 28.70→22.11ms였다. 이 값은 단일 로컬 경로에서 순차 측정한 관측값이다. 안전한 인증 fixture가 없어 보호 페이지의 실제 TTFB 및 갱신 후 RSC 쿠키 전달은 라이브로 측정하지 못했다. 기존 Proxy 테스트와 서버 API 테스트는 각 경계를 별도로 검증한다.
