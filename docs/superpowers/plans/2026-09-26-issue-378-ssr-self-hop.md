# #378 SSR self-hop 제거 계획

## 결정과 범위

- #380(#377)이 아직 미병합이므로 최신 `origin/main`에서 #378 작업 트리를 분리하고 #380 head를 반영해 구현한다. 최종 PR은 #380 병합 후 `main` 기준 diff를 확인해 연다.
- Server Component와 서버 prefetch의 남은 `서버 → 프런트 /api → 백엔드` 조회를 감사하고, 필요한 조회만 `server-only` 백엔드 직행으로 바꾼다. #362의 `features/session/server/api.ts` 패턴을 재사용한다.
- 브라우저의 보호 API 요청은 기존 프런트 `/api` Route Handler를 유지한다. 현재 백엔드는 `Authorization: Bearer`를 요구하고 브라우저 JavaScript는 `HttpOnly` 액세스 토큰을 읽을 수 없다. 클라이언트 토큰 메모리 저장, 로그인·갱신 방식 변경, Route Handler 제거는 이 이슈 범위가 아니다.
- 서버·브라우저의 **호출 경로와 얇은 endpoint 함수만** 분리한다. 응답 타입, 공통 fetch/오류 처리, 쿼리 키를 불필요하게 복제하지 않는다.

## Herdr 실행 역할

- Codex는 orchestrator로서 #378 범위 확정, 기준선 측정, 작업 지시, diff 검토, 독립 검증, 커밋·PR 및 최종 인계를 책임진다.
- Herdr의 표시 이름 `w5`인 pane을 worker로 사용한다. 현재 확인된 실제 pane ID는 `w1:pZ`이며 Grok 에이전트가 대기 중이다. ID는 세션마다 달라질 수 있으므로 실행 직전에 `herdr pane list --workspace "$HERDR_WORKSPACE_ID"`로 `w5`를 다시 찾는다.
- Codex가 #380 head가 반영된 분리 작업 트리와 필요한 작업 환경을 준비하고, worker에게 변경 대상·완료 조건·작업 경로를 전달한다. worker는 코드와 필요한 검증을 수행하고 결과 및 남은 위험을 보고한다. Codex는 worker 결과를 그대로 채택하지 않고 실제 diff와 테스트 결과를 확인한다.
- worker가 승인 대화상자 등으로 막히면 Codex가 상태와 출력을 확인해 사용자에게 필요한 입력을 요청한다.

## 실행 단계와 확인 방법

1. **대상 감사**: 서버에서 호출되는 member 조회(`getMe`, `getMeForEdit`, `getMyReportStats`, 보고서 목록 등)와 session 조회(`detail`, `waitingRoom` 등)의 실제 호출 경로를 열거한다. 이미 직행하는 호출과 브라우저 전용 호출은 제외한다. → 대상별 현재 경로와 변경 후 경로가 표로 남아야 한다.
2. **인증 경계 확인**: 보호 페이지 문서 요청에서 Proxy가 갱신한 쿠키를 서버 조회가 읽는지 확인한다. 서버의 외부 백엔드 `fetch`는 프런트 Proxy를 다시 거치지 않는다. self-hop 자체가 항상 재갱신이나 쿠키 유실을 일으킨다고 가정하지 않는다. → 새 토큰 전달과 `Authorization: Bearer` 구성을 경계 테스트로 검증한다.
3. **최소 변경**: 해당 서버 조회만 server-only endpoint로 전환한다. 클라이언트 BFF, Route Handler, Server Action, 캐시 정책은 유지한다. → 결과 데이터·오류 처리·hydration 동작이 동일하고 브라우저 번들에 server-only 모듈이 들어가지 않아야 한다.
4. **검증**: 관련 테스트, 전체 Jest, lint, typecheck, build, `git diff --check`, 사용자에게 보이는 경로의 브라우저 QA를 수행한다. → 결과를 PR에 기록한다.

감사 결과 #380 head 기준 실제 대상은 대기실 페이지의 상세·대기실 조회, 수정 페이지의 상세 조회, 프로필 기록 페이지의 통계·이력 조회, 세션 결과 페이지의 상세·내 리포트 조회, 참여자 리포트 페이지의 상세·내 리포트·전체 리포트 조회다. #380이 제거한 루트 `me` 서버 조회와 공개 세션 페이지의 대기실 prefetch는 이 이슈에서 다시 만들지 않는다.

## 변경 전후 측정 기록

- 동일한 배포 모드, 백엔드, 페이지, 인증 상태, 캐시 조건에서 변경 전후를 측정한다. 공개 페이지와 인증 페이지를 분리한다. 인증 페이지에 안전한 전용 계정/fixture가 없으면 실제 사용자 토큰을 사용하지 않고 해당 측정을 미실시로 기록한다.
- 페이지별로 Document TTFB, 문서 응답 완료 시간과 SSR의 프런트 `/api` self-call 수, SSR→백엔드 호출 수를 기록한다. Next 스트리밍은 서버 조회가 끝나기 전에 문서 첫 바이트를 보낼 수 있으므로 TTFB만으로 이 변경의 효과를 판단하지 않는다. 가능하면 warmup·반복 횟수, 중앙값과 p75, 측정 환경과 기준/변경 commit SHA를 함께 남긴다. 네트워크 기록 또는 서버 로그로 호출 경로를 확인한다.
- `self-call 1→0`은 구조적 감소다. 백엔드 호출 수가 함께 줄었다거나 브라우저의 `/api` 요청 수가 줄었다고 추론하지 않는다. TTFB 및 전체 로드 시간 개선 여부는 실제 측정값으로만 판단한다.
- 인증 만료/갱신 시나리오도 별도로 확인한다. 갱신 성공, 쿠키 반영, 401 처리 결과를 기록하고 토큰 값은 로그·문서·PR에 남기지 않는다.
- 측정 표는 `페이지 / 인증·캐시 조건 / 기준 SHA / 변경 SHA / 반복 횟수 / TTFB median·p75 / 응답 완료 median·p75 / self-call 수 / 백엔드 호출 수 / 비고` 열로 남긴다. 수치가 없으면 원인과 확인 가능한 구조적 결과를 구분해 적는다.

## 기대 효과와 트레이드오프

- 기대 효과: SSR의 불필요한 프런트 왕복과 Proxy 재진입을 제거한다. 해당 조회의 Document TTFB가 줄어들 가능성이 있다.
- 비용: 서버와 브라우저에서 같은 endpoint의 얇은 호출 함수를 따로 유지해야 하므로 경로 간 동작 차이를 테스트해야 한다.
- 브라우저 호출은 여전히 프런트 `/api`를 거친다. 액세스 토큰을 메모리로 옮기면 이 왕복을 없앨 수 있지만, JavaScript에 토큰을 노출하고 로그인·갱신·새로고침·SSR 인증 흐름을 다시 설계해야 한다. 현재 이슈의 이득을 얻는 데 필요한 변경이 아니다.

## 결정 과정과 최종 기록

- 구현 전 ADR에 실제로 검토한 대안과 선택 근거를 남긴다. 최종 PR 본문의 `작업 내용` 또는 `참고 사항`에도 아래 비교와 구현 후 확인된 결과를 요약한다. 로컬 계획·저널만 읽어야 판단할 수 있게 두지 않는다.

| 선택지 | 얻는 것 | 감수할 비용·선택 판단 |
| --- | --- | --- |
| 현재 self-hop 유지 | 서버·브라우저가 같은 endpoint 함수를 사용 | 불필요한 프런트 왕복과 Proxy 재진입이 남아 #378 목적을 달성하지 못함 |
| **서버 직행 + 브라우저 BFF 유지(채택)** | SSR self-hop 제거, 브라우저 JavaScript에 토큰 비노출, 기존 로그인·갱신 유지 | 서버·브라우저의 얇은 endpoint 함수가 나뉘어 경로·옵션 불일치 가능. 공통 타입·fetch·쿼리 키 재사용과 양쪽 경로 검증으로 관리 |
| 브라우저 액세스 토큰 메모리 저장 후 직접 호출 | 브라우저의 BFF 경유도 제거 가능. 백엔드 CORS는 `Authorization` 헤더를 허용 | JavaScript 토큰 노출, 새로고침 후 재발급, 로그인·갱신·SSR 인증 재설계 필요. 이번 SSR 개선에 비해 변경 범위가 큼 |
| 백엔드가 쿠키를 직접 인증 | 브라우저에서 `Bearer` 헤더를 만들 필요 없음 | 백엔드 인증 계약·쿠키 범위 변경과 CSRF 검토가 필요해 프런트 #378 범위를 벗어남 |
| 하나의 endpoint 함수에서 실행 환경에 따라 경로 분기 | endpoint 함수 중복 감소 | 호출 경로가 숨겨지고 `server-only` 경계가 약해짐. 이미 공통 전송 함수가 있으므로 작은 wrapper 분리를 택함 |

- PR에는 **무엇을 선택했는지 → 어떤 비용을 감수했는지 → 그 비용보다 중요한 근거가 무엇인지**를 명시한다. 근거는 코드 경로, 인증 계약, 테스트, 전후 측정값에 연결한다. 위 표의 예상 효과와 구현 후 관찰된 효과가 다르면 그 차이와 남은 위험도 적는다.
- PR 측정 결과에서는 SSR self-call 감소, 백엔드 호출 수, Document TTFB를 따로 기록한다. 브라우저 요청 수나 전체 체감 속도를 측정 없이 개선 효과로 주장하지 않는다. 측정하지 못한 항목은 이유를 남긴다.

## 완료 조건

- 감사에서 확인한 대상 SSR 조회에 self-hop이 남지 않는다.
- 브라우저 인증 요청과 Route Handler 동작은 유지된다.
- 인증·데이터·오류 처리 회귀가 없고 측정 결과, 대안별 트레이드오프, 채택 근거와 남은 위험이 PR에 기록된다.
- Ready PR을 `main` 대상으로 열고 리뷰에 인계한다. 병합과 이슈 종료는 별도 요청 전까지 하지 않는다.
